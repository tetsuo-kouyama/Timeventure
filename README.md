## 1. サービス概要

アプリ名: Timeventure

このサービスは、タイマーに放置ゲームの要素を組み合わせることで、タイマーを起動する心理的なハードルを下げ、継続的な習慣化をサポートするアプリです。

- タイマーを起動している間、ゲーム内のキャラクターが自動で冒険します。
- ユーザーが作業や勉強に取り組む時間がそのままキャラクターの冒険時間となり、タイマーを起動すること自体が楽しみになるようなサービスを目指しています。

**放置ゲームとは何か？**

- 放置ゲームは、一般的に「プレイヤーが直接操作していない間にも、ゲーム内の進行や成長が続くゲーム」を指します。
- プレイヤーの継続的な操作ではなく、「時間の経過」を利用した成長システムを採用したゲームのことです。

---


## 2. このアイデアはどこから生まれたか

### 2-1. きっかけとなった体験・感情

プログラミング学習中にタイマーで時間管理をしていましたが、長期化するにつれて「終わりのないシャトルラン」のような息苦しさを感じ、使わなくなってしまいました。

そこで、タイマーにゲームの楽しさを取り入れられないかと考え、放置ゲームをタイマー代わりに使ってみました。

「キャラクターを冒険に出す → 冒険が終わったら勉強を中断する → 休憩しながら冒険の結果を確認する → 再び冒険に出す」というサイクルを作ることで、時間を区切って学習しながらゲームを進める楽しさも得られるようになりました。

一方で、一般的な放置ゲームでは「帰還まで残り42分」のように、ゲーム側によって待ち時間が決められています。そのため、「25分だけ勉強したい」と思っていてもゲームの進行に合わせて時間を調整する必要があり、時間管理にゲームを利用しているはずが、逆にゲームに生活リズムを合わせることになってしまいました。

この経験から、自分で決めた時間だけキャラクターが冒険する放置ゲームがあれば、タイマーとして使えるのではないかと考えたことが、このアプリを開発しようと思ったきっかけです。


---

### 2-2. なぜそれが「気になった」のか

初めの頃は「25分集中して勉強しよう」という気持ちで取り組んでいましたが、次第に「タイマーを開始したら25分勉強しなければならない」と考えるようになってしまいました。

一方、放置ゲームをタイマー代わりにしていた時は、「冒険が終わるまでの待ち時間を有効活用するために勉強しよう」と前向きに考えることができました。

どちらも「一定時間勉強する」という行動自体は同じですが、時間の捉え方によって取り組み始める際の心理的ハードルが大きく変わることに気づきました。

## 3. 課題の整理

### 3-1. 表に見えている困りごと

**タイマーを継続して使う中で生まれる問題**

- タイマーを開始することに義務感や心理的な負担を感じる
- 単調な繰り返しによって、タイマーを使うこと自体に飽きてしまう
- その結果、タイマーを使わなくなってしまう


**タイマーを使わなくなることで生まれる問題**

- 作業と休憩の境界が曖昧になり、ダラダラと作業を続けてしまう
- 必要以上に長時間作業を続け、疲れてしまう
- 集中する時間と休憩する時間のメリハリをつけにくくなる

---

### 3-2. 本当に解決したい課題は何か

タイマーによって作業と休憩を区切ることの価値は理解していても、タイマーを使うこと自体が負担となり、継続できなくなってしまうことです。

---

## 4. 想定ユーザーについて

### 4-1. 想定しているユーザー

**ターゲット**

勉強や練習などにタイマーを使った時間管理をしていたものの、義務感や退屈さを感じて継続できなくなってしまった人

**代表的なユーザー像**

- 試験勉強や資格勉強に取り組む学生・社会人
- プログラミングやタイピングなどの学習・練習に取り組む人
- 楽器や筋トレなどの反復練習に取り組む人

年齢や性別などの「属性」ではなく、「状況・課題」に着目してターゲットを設定しています。

---

### 4-2. 自分とユーザーの距離

想定ユーザーは自分自身でもあります。

- タイマーによる時間管理の重要性は理解しているものの、起動することを億劫に感じてしまう
- 現在はタイマーを使わず、「疲れるまで」「区切りのいいところまで」と作業を続けてしまうことが多く、作業と休憩の切り替えがうまくできていない
- もう一度タイマーを使った時間管理を習慣にしたいと考えている
- 「作業を始めるためにタイマーを起動する」のではなく、「ゲームの冒険を始めるためにタイマーを起動する」と捉えることで、より気軽にタイマーを使い始められるのではないかと考えている

---

### 4-3. 実際に使われる可能性について

**まず最初に使ってくれそうな人**

- 既存のタイマーでは継続できず、自分に合ったものを探している人

**利用シーン**

- 勉強や作業を始めるとき
- 作業と休憩を一定の時間で区切りたいとき

**今の生活の中で、代わりに使っているもの・方法**

- 放置ゲームの待ち時間をタイマー代わりにする
- タイマーとゲームをそれぞれ用意し、作業中はタイマー、休憩中はゲームと切り替えて使う
- タイマーを使わず、自分の感覚で作業と休憩を切り替える

**それを置き換えてまで使う理由**

- 「タイマーの終了」と「冒険結果の確認」を結びつけることで、時間が経過した先に楽しみを作れる
- タイマーとゲームを別々に用意する必要がなく、一つのサービスで作業と休憩のサイクルを作れる
- キャラクターの育成や冒険を自動化し、ユーザーの操作を最小限にすることで、作業中にゲームへ意識が向きすぎることを防ぐ

---

### 4-4. ユーザーがサービスを導入して利用するまでのイメージ

**このサービスを知るきっかけ**

- 作業や勉強の時間を区切りたいが、通常のタイマーでは継続することが難しいと感じたとき
- 楽しみながら続けられるタイマーを探しているとき

**最初の一歩（登録・導入）で、ユーザーは何をする必要があるか**

1. 「ゲストログイン」または「新規作成」からサービスを利用開始する
2. 冒険するキャラクターを1体作成する
3. タイマーの時間を設定し、最初の冒険を開始する

**利用を続ける理由は何か？**

- タイマーを使うたびにキャラクターが冒険し、少しずつ成長していくため、継続してタイマーを使う楽しみが生まれる
- 冒険を重ねることで、新しい敵やアイテムなどが図鑑に記録され、タイマーを使い続けてきた成果が目に見える形で残る

## 5. 既存サービス・競合調査

### 5-1. 自作サービス「ポモクエ」の振り返り

- URL: https://github.com/tetsuo-kouyama/pomodoro-quest-eventlog

#### 課題点と改善策

1. タイマーとゲームのバランス

    課題:

    - ゲーム体験を充実させるため、アイテムの装備やクエストなどの機能追加を検討していた
    - しかし、機能を増やすほどユーザーに求める操作が増え、休憩時間内にゲーム操作を終えられなくなる可能性があった

    改善:

    - キャラクターの育成や装備変更などは自動で行い、ユーザーが行う主な操作を「キャラクターの作成(1体のみ)・タイマー設定・冒険開始」の最小限に絞り込む
    - タイマーの終了後は30秒以内に冒険結果を確認し、次の冒険を開始できることを目指す

2. タイマー画面が集中を妨げる可能性がある

    課題:

    - タイマー起動中に冒険イベントをリアルタイムで表示していたため、ゲームの進行が気になり、作業への集中を妨げる可能性があった

    改善:

    - タイマー起動中は冒険イベントをリアルタイムで表示せず、タイマーの終了・停止後に冒険結果をまとめて表示する

3. タイマーの自由度が低い

    課題:

    - ポモドーロを意識した時間設定にしていたため、ユーザーが自分の作業内容や生活スタイルに合わせて自由に時間を設定できなかった

    改善:

    - アプリ側で決められた冒険時間から選択するのではなく、5分〜180分まで、5分単位でユーザーが自由に設定できるようにする

### 5-2. 参考にしたアプリ

#### Godville

- URL: https://play.google.com/store/apps/details?id=com.godvillegame.android&hl=ja
- 特徴: ユーザーによる操作をほとんど必要とせず、キャラクターが自動で冒険や成長を続ける放置RPG
- 参考にした部分:

  「キャラクターを自分で育成する」のではなく、「自動で行動・成長するキャラクターを見守る」というゲームシステムです。

  ユーザーに求めるゲーム操作を最小限にでき、タイマーとの相性が良いと考え、このシステムを参考にしました。

---

### 5-3. 似たサービスの調査

#### 異星フォーカス

- URL: https://play.google.com/store/apps/details?id=work.byland.exocus&hl=ja
- 特徴：集中した時間に応じて惑星が成長していくタイマーアプリ

#### Quest Timer

- URL: https://techio-code.github.io/quest-timer/
- 特徴：ポモドーロとRPGを組み合わせ、集中することでゲームを進められるアプリ

---

### 5-4. それでも自分が作りたい理由

#### 既存サービスに感じたズレ

- 異星フォーカスは、タイマーを途中で中断すると報酬を獲得できない仕組みなので、自分にとって「設定した時間を最後までやり切らなければならない」という負担につながると感じた

- Quest Timerは「タイマーとRPGを組み合わせる」という点で共通しているが、装備変更などユーザー自身がゲームを操作して進める要素がある

#### 作りたい理由

タイマーにゲーム体験を加え、継続的な習慣化を促すサービスはいくつか存在しますが、できるだけ負担なく使えるタイマーを作りたいと考えています。

---

### 5-5. 差別化を「体験価値」で表現する

Timeventureでは、タイマーを最後まで完了することやゲームを操作することを目的にするのではなく、「自分が決めた時間だけキャラクターを冒険させ、その時間を作業に活用する」という体験を提供したいと考えています。

---

## 6. このサービスで提供したい価値

### 6-1. ユーザーの変化

- 行動の変化
  - タイマーを起動することへの負担が減り、作業や勉強を始めるきっかけを作れる
  - タイマーを使って作業と休憩を区切る習慣を継続しやすくなる

- 気持ちの変化
  - 「キャラクターを冒険させよう」というゲーム感覚で、気軽にタイマーを起動できる
  - タイマーの終了後に冒険結果を確認する楽しみが生まれ、次も使ってみようと思える

- 考え方の変化
  - タイマーに対するネガティブな捉え方が和らぐ

---

### 6-2. 価値を一文で表す

このサービスは、タイマーを使わなくなってしまった人が、ゲームの楽しさをきっかけに、再びタイマーを使う習慣を作ることをサポートします。

## 7. このアプリで実現すること

### MVPで作る機能

#### 1. 認証

- メールアドレス・パスワードによる登録・ログイン
- ゲストログイン

#### 2. キャラクター

- 新規登録時にデフォルトのキャラクターを自動生成
- キャラクター名はステータス画面から変更可能

#### 3. タイマー

- 集中タイマー
- 休憩タイマー
- 集中タイマー終了後、休憩タイマーへ自動で移行
- タイマーの中断
  - 中断した時点までの冒険結果を反映
- 設定した集中時間・休憩時間の変更

#### 4. 冒険

- タイマー起動中のイベント生成
  - 戦闘
  - アイテム取得
  - 装備の自動変更
  - アイテムの自動売買
  - HP減少時の休憩・回復
- タイマー終了・中断後の冒険結果サマリー
- 冒険ログの一括表示

### 本リリースで作る機能

- ゲストアカウントから本アカウントへの移行
- 初回ログイン時にウィザード形式で初期設定を行う
  - キャラクター名
  - 集中時間・休憩時間
- ポップアウト機能(Document Picture-in-Picture API)
- タイマー終了時の通知
  - 集中タイマー終了時の通知
  - 休憩タイマー終了時の通知
- タイマー設定のスロット増加
- 図鑑機能(モンスター・アイテム・フィールド)
- キャラクター画像
- ゲームバランス・UIの調整

## 8. このアプリの懸念点とその対策

### 懸念点① 長期的な目的が弱い

ゲーム部分ではユーザーによる操作を最小限としているため、キャラクターの成長を見守るだけではゲーム体験が単調になり、長期間利用する目的が弱くなる可能性があります。

#### 対策

モンスター・アイテム・フィールドなどの図鑑を用意します。
キャラクターの成長とは別に収集要素を設けることで、「図鑑を完成させる」という長期的な目標を作ります。

### 懸念点② ゲーム操作を減らすことでゲーム性が弱くなる

作業を妨げないようにゲーム操作を最小限にする一方で、ユーザー自身がゲームに介入できる場面が少なく、ゲームとしての楽しさを感じにくくなる可能性があります。

#### 対策
キャラクターの行動イベントを充実させ、「キャラクターの行動や成長を見守る楽しさ」を強化していきます。

### 懸念点③ タイマーの設定時間によってゲームバランスが崩れる

集中時間を5分から180分まで自由に設定できるため、設定時間によってゲームの進み方に大きな差が生まれる可能性があります。

#### 対策

冒険イベントを経過時間に応じて発生させ、同じ冒険時間であれば、タイマーの設定時間によって大きな差が生まれない仕組みにします。

例えば、「15分×4回」と「60分×1回」で発生するイベント数を同程度にし、どちらかが圧倒的に有利にならないようにします。

### 10-2. 技術選定の比較検討

| 候補 | 採用/不採用 | 理由 |
| --- | --- | --- |
| Ruby / Rails API | 採用 | ジェネレーターによるコード生成や「設定より規約」という特徴から、規約に沿って素早くアプリを開発できると考え採用<br>画面描画はReactに任せ、Railsは認証・データ管理・ゲームロジックを担当するAPIとして使用する |
| React | 採用 | タイマーの状態管理が必須となるため、画面遷移を抑えつつ状態に応じてUIを変化させやすいReactを採用|
| Next.js | 不採用 | ゲームロジックをRails APIに集約するため、SSRなどの機能を必要としない<br>また、サーバー機能を利用すると構成や運用コストも増えるため、SPAとしてReactを採用 |
| Neon | 採用 | PostgreSQLのホスティング先として使用<br>無料枠があり、管理画面からテーブルの確認やSQLの実行もできるため、開発・運用時のデータ確認がしやすい |
| Supabase | 不採用 | PostgreSQLに加えて認証やAPIなどのバックエンド機能を提供しているが、今回は認証・APIをRails側で実装するためオーバースペックと判断し不採用 |
| Document Picture-in-Picture API | 採用 | タイマーを常に最前面に表示できるポップアウト機能を実現するために使用する<br>非対応のブラウザ(Safariなど)もあるため、通常のタイマー画面でも利用できる設計にする |

---

### 10-3. 今回チャレンジしたい点

- React + Rails APIによるフロントエンド・バックエンド分離構成
- Document Picture-in-Picture APIを利用したタイマーのポップアウト表示
- キャラクターの行動や進行の自動化

---

### 10-4. 不安な点

- React + Rails APIの構成ではそれぞれを別サービスとしてデプロイし、API通信を行うための設定が必要になるため、初期のデプロイ環境構築や調整に時間がかかる可能性がある
- Reactについては学習しながらの開発となるため、想定以上に実装に時間がかかる可能性がある

#### 対策

- テストアプリを作成し、事前にReact + Rails API構成でのデプロイを確認することで本サービスのデプロイをスムーズに行えるようにする
- Railsについては、これまでに作成したアプリの知識を活用し、Reactを中心に必要な技術をキャッチアップしながら開発を進める
- 開発中に必要性を感じたライブラリや追加機能は適宜メモしておき、MVPに必須でないものは完成後に検証した上で導入を判断する

#### 現時点でのキャッチアップ

学習済み

- TypeScriptの基本的な型の仕組み
- Reactの基礎（コンポーネント、Props、useState、useEffect）
- ReactとRails API間の基本的な通信方法

調査中

- CORSの設定
- 本番環境でのAPI URLの管理
